# FindMe — 应用架构

> To-Be。以 [Overview](overview.md) 的赛博分身愿景、[BA](ba.md) 的 B1–B7 为需求，以 [DA](da.md) 的领域语义为契约。本文描述逻辑模块和应用特性；[第一阶段范围](delivery/phase-1-personal-understanding.md)定义本阶段需要贯通的使用结果，不声明新 API、服务或数据库已存在，也不要求一个模块部署一个服务。

## 1. 应用边界

应用围绕同一份可修订的个人理解组织能力。持续对话、主动引导、学习反馈和语料导入共同提供新信息；开导、建议、诚实挑战、学术与方法引导共同使用这些理解。总览、专题、个人发展诊断和个人使用说明承担综合呈现，不能成为唯一交互或最终产品目标。

“赛博分身”描述持续了解本人并保持独立判断的产品愿景。当前模块划分承接已有工程职责；Agent、人格蒸馏 Skill 或其他未来形式均是实现候选，不定义新的个人真源，也不构成本阶段的必经流程。第一阶段先使个人理解在真实对话、阅读与纠正中可用，未来的分身表现按相应场景验证。

客户端只负责交互、呈现、用户选择与授权，核心解释、证据检索、认识修订和租户校验在应用侧执行。`apps/app` 的手机 H5 与桌面浏览器使用同一业务语义，不各自维护一份人格 prompt 或个人记忆。

外部来源经可选 adapter 进入核心接入边界；原生对话、经历和学习反馈直接进入同一边界。来源经证据/经历与解释形成当前认识，对话、建议及综合呈现使用当前认识；新表达、纠正和实际结果再次修订相关认识。不是每条输入都需要生成人格结论。

正式产品的手机 H5 与桌面浏览器经同一 `apps/app` 客户端和账号身份访问同一云端 Core；服务端管理对话、个人理解、诊断状态、证据用途与结果版本。可选桌面采集器只提交授权材料和增量，不是唯一数据副本、唯一推理节点或登录前提。设备缓存和离线草稿不是独立个人模型。

公共学术与方法材料位于独立的内容边界，为提问、解释、支持和候选做法提供有来源的依据。用户对材料的认同、质疑及尝试反馈进入个人来源链，材料本身不能证明用户具有某项特征。Obsidian vault、AgentsView 目录、历史数据库和离线脚本不在核心的运行依赖中。

| A2 来源接入 | 原生/导入统一受理、批次预览、格式校验、来源归属、幂等、原文与历史衍生结果分流；adapter 可插拔 | SourceRecord、接入结果与失败理由 | B2、B7 |

A1–A7 承担个人理解的形成、使用和修订，A9 提供有来源的知识支撑；第一阶段可先使用少量已核验、与当前问题有关的内容，不等待完整知识库。A8 的结构化验证和 A10 的完整框架按需调用。A8 只处理题组/量表式验证，不与 A10 的解释型框架混为一种“测评”；A10 可复用 A1 的交互、A4/A5 的语义推理和 A6 的计划承接，不要求独立 Agent 或微服务。现有 M-A/M-O/M-X 编号保留为源码定位，不升级为这张目标能力地图的权威编号。

### 跨模块能力

**身份与个人租户边界。** 从服务端认证身份确定租户；每项读写、检索、任务、缓存、引用解析和导出都验证归属。当前单用户实现不能被视为已具备这些能力。无组织管理员代看其他个人画像的业务入口。

**数据控制。** 来源启停、展示隐藏、分析排除、导出、撤回和受控删除由明确命令触发，不能互相混用；删除或排除传播到派生认识、缓存和未执行任务。公共素材与私人资料分开。维护公共内容的职责不产生查看用户资料的权限，更不是企业管理员管理员工。完整导出覆盖已持有的个人作答、认识、修订、反馈、尝试及必要来源关系；不包含认证 secret，未保存在核心的外部原文不能承诺随包带走。

**LLM 与任务执行。** 沿用 M-X2 作为唯一模型出口；结构化输出校验、调用预算、失败恢复、版本与来源记录为共同能力。模型提出候选，不直接决定租户权限、证据 ID、生命周期或用户是否已接受建议。

**认识形成策略。** A4/A5 共用版本化 Epistemic Policy：程序先执行权限、用途资格、版本、问题预算等可确定 gate；模型处理回应意图、关键不确定性、候选解释、范围表述等语义任务；结果再经过对应 validator 才能创建 QuestionRecord 或发布 ClaimRevision。普通支持或解释不必强制产生新问题或新认识。Prompt 只是该策略的一项实现版本，不能独自成为产品规则真源。

**独立判断与支持。** 对个人判断使用同一套证据、反例和修订标准，不因用户希望被认可、被严厉批评或听到“揭穿”而改变。A1 可表达理解与支持，A5 仍需说明具体判断的依据、替代解释和未知；用户不同意不作为自欺证据。系统发现自己的误读时，由同一纠正链更新后续回应。

**Insight Analysis Profile。** 在同一 A4/A5 管线内允许启用一个更强的洞察 profile，而不是新增第二套“Insight 真值库”。该 profile 明确产出 presented problem、problem reframe、life-structure gap、tension、candidate hypothesis、alternative explanations、discriminating question / experiment candidate；每项必须带可见依据和适用范围。可持久化的认识仍进入 Claim/ClaimRevision，未决分歧进入 KnowledgeGap，行动候选进入 A6；GenerationRecord 只保存可复核结构化输出与版本，不保存隐藏 chain-of-thought。

**质量检查。** 引用可定位、摘录忠实、归属正确、时间适用、论断与依据相关分别检查。模型自评 confidence 不承担质量门职责，不因引用 ID 存在就宣称解释正确。

## 3. 核心协作流程

### 3.1 零导入的对话与引导探索

A1 读取用户选择和可用认识，通过 A4 获得一个低负担入口。没有背景时用中性具体经历，不默认用户存在问题。回应经 A2 保存；A3 按需要组织事件，不强求每条话都有主题、情绪或完整事件。

A4 先判断可以直接支持、解释或提出建议，还是需要补背景、找反例、开放探索或结束；A5 在证据允许时给有限观察。A7 展示依据、范围与未知。用户不必先完成访谈或拿到完整报告才获得帮助。A1 提供事实、情境、程度和解释等纠正入口。

提问理由、问句和已呈现的候选解释保留在 QuestionRecord，以便区别自然表达和受提示回应。用户未回答仅记未回答，不产生人格推断。

### 3.2 历史材料接入

adapter 解析外部格式，生成核心接入对象；A2 验证来源类型、租户及幂等键。原始记录、外部抽取和外部洞察分别标明，不要求从旧 L2/L3 伪造本地 L1。

A3 对相关片段建立来源映射，保留必要上下文；没有可读原文的结果仍可作为带出处的未验证历史认识，不能生成“原文已核验”状态。已确认归属且通过同源检查的结果进入 A5，不要求全量重新分析。

A4 可用历史线索减少重复提问，但不能只挑符合旧画像的材料。adapter 停用或来源暂不可达，不得导致原生采集、当前认识及可用的本地证据副本失效。

### 3.3 纠正、反例和新情况

A1 接受事实纠正、解释异议、范围缩小、程度调整、状态已变或单纯风格偏好。A3 保存用户补充及其来源；A5 定位受影响的 ClaimRevision，检查依赖，并将事实错误与观点分歧分开处理。

错误事实使其派生解释失效或待复核；解释异议保留争议或替代解释，不伪装成已证伪；明确的使用排除立即生效，不等待模型同意。A7 更新当前视图并解释修改原因。再次对话、生成建议或读取综合认识时，都应用当前版本；不能只更新报告文字而让后续回应继续使用旧误解。

### 3.4 从理解到尝试

A6 基于用户目标、现实约束及必要认识提出建议，不要求先接受某个人格结论。采用通用方法或行动模板时，另引用 A9 已审核发布的内容及适用边界；模型不能仅凭“这个人似乎如此”就编造某种方法有效。用户确认后才创建 ActionTrial；修改或拒绝仍是正常结果。

用户报告行动及结果，经 A2/A3 成为新记录和经历。A6 区分未执行、执行但结果不明、达到目标和需要调整；A5 据此修订相关认识，不自动把一次结果解释为因果证明。A7 展示尝试结果及仍未知的部分。

本轮只设计 App 内支持，不自动调用外部日历、发送消息或执行生活决定。提醒等外部动作须在具体需求中单独授权。

### 3.5 提问、画像与趋势

临时提问由 A4 选择针对性证据，不每次使用同一“最新 N 条”窗口。画像从当前可用 ClaimRevision 投影；历史快照保留当时证据、版本和范围，不能变成新的独立证据。

趋势必须说明是事件/状态发生变化、覆盖变化、解释被修正还是模型版本变化。两个摘要文案不同不足以证明人发生了变化。

### 3.6 可选结构化验证与版本化结果

A4 或用户选择结构化验证；A9 提供已发布且适用的 AssessmentDefinitionVersion。A8 固定题目/计分版本，接收作答，按缺失/跳过规则计算或明确不出结果，再由 M-X2 解释确定性结果。反思题无需分数，也不伪称量表。

作答进入个人来源链，AssessmentResult 回指作答与规则；A5 在范围内使用它，不把一份作答和由它计算出的结果当成两份独立证据。用户可继续观察、进入 A6 或结束；复测只有在工具/版本/适用条件允许比较时才形成数值趋势。

### 3.7 编辑内容与角色的发布链

A9 管理 ContentSource → ContentSourceVersion → ContentEvidenceChunk → ContentClaim → ContentCard → ContentRelease。只有已审核、生效且适用的内容可被推荐；撤回后阻止新调用，依赖旧内容的重要结果可标需复核。自建内容和 AI 草稿明确来源与局限，不能伪装成已有研究证据。

RoleDefinitionVersion、ActionTemplateVersion 与工具定义引用内容发布和版本。A1 保留实际使用的角色/prompt 与提问刺激；A6 保留具体建议及用户接受时的模板版本。修改配置不能静默回写过去的对话、作答或计划。

公共内容审核与个人表达采集是两种流程：个人输入不需要等待编辑审批才保存或获得帮助。第一阶段可以采用小范围版本化发布文件，不需要完整 CMS 或额外服务。

### 3.8 三观澄清与价值差异处理

A1 接收用户自述、向往、感到的要求及自定义原则，A3 组织其来源与实践情境，A5 形成有类型、范围和版本的认识；A7 按世界观/人生观/价值观投影，并展示未知、相互支持或尚未解释的差异，不生成固定学派人格。

用户偏好的探索视角单独配置，不预填三观。A4 仍提供中性问题和反例，不因用户选择道家就只检索道家式回答。发现差异时先检查事实和实际可选项，再邀请用户选择理解差异、尝试改变、调整环境、修订原则或暂不处理。A6 只在用户选择行动后接续。

### 3.9 多角色视角对照

A1 接受用户主动选定的事件/行为/对话及视角；A3 构建同一个带版本的情境包，保留发生事实/本人报告、已知感受、约束、问题和未知。A9 提供已发布的 RoleDefinitionVersion 及本次相关文本依据。M-X2 按角色分别生成受契约约束的解释，由 A5 核验事实一致、来源支持和推演标记，A7 在同一比较维度下呈现。

每个视角返回：本次关注点、所依据的文本及诠释、必要假设、可能的理解和行动、代价与适用边界、未知/不输出原因。对照只概括差异，不宣称角色多数同意就是真的，不将“最像该人物”当质量标准。可先让用户表达自己的初步看法，再展示视角，便于辨认提示带来的影响；不强制用户先作答。

A1 将用户认同/反驳/改写的部分与已呈现内容关联保存；A5 不以这些回应独立证明先前模型判断。用户要行动时将其选择交给 A6，而非让角色直接执行；用户只想理解时到此结束。

角色资产可封装为声明式 role skill/profile，由既有 A9 和 M-X2 使用，不另增角色专属模块、独立 Agent 平台或可任意执行工具的插件。这里的 role skill 只是一种可选内容封装，不是个人赛博分身的既定实现。先共享情境再分别生成即可；是否并行属于技术实现选择，不作为多视角成立的前提。

### 3.10 来源评估与证据作用修订

A2/A3 接收更正并保留原始版本，分别记录来源质量和与特定 ClaimRevision 的关系评估；A4 先检查权限与用途资格，再选择材料；A5 综合支持、挑战、范围及相关性形成置信说明；A7 展示理由和纠正入口。评价定义见 DA §5.4–5.6，不增加独立评分模块。

归属、时间、上下文、分析范围或评估规则变动时，按来源 → 关系 → 认识 → 视图/对照/建议定位受影响对象；A5 复核或标为待复核，A4 不再召回被撤销关系。禁止只改显示分数、不改变下游使用。需延后重评时明确状态，已失效结果不得继续冒充当前有效。

规则性检查由代码执行；需语义判断的部分生成有理由且可质疑的候选。用户校正、程序核对与模型自评不同源，不能把所有评估写成同一确定结论。旧生成在发布前复查输入与评估版本，必要时丢弃或重排受影响任务；更正本身不因模型不可用而丢失。

### 3.11 外部框架完整运行

A9 提供已发布且可追溯的 FrameworkDefinitionVersion；A10 启动 FrameworkRun 时固定该版本，不在运行中静默升级。框架入口先保存用户确认的基础信息，再按定义的 dimension/order/question policy 逐步运行；每次回答仍经 A2/A3 进入个人来源链。

框架可以有两种评估方式：确定性规则由程序执行；无法预先写成公式但框架本身允许语义 rubric 时，由 M-X2 依据固定 rubric 生成候选，再由 validator 检查维度、允许等级、证据引用和输出结构。两种方式必须显式标识，不能把语义判断包装成确定性量表分数。

HUMAN 3.0 的目标运行以 Dan Koe 公开原始框架为准：基础信息 → Mind / Body / Spirit / Vocation adaptive interview → Level / Phase 判断 → 跨象限关系 → Lifestyle Archetype / Metatype 等框架内综合 → core problem → 原协议实际输出的阶段计划（30 天、90 天、6–12 个月；页面宣传段与输出段的差异见 R01）；Channels 等高级动态只有在定义要求且证据足够时进入。Adaptive follow-up 只能用于澄清框架已定义的概念与 rubric，不能借“深入”增加框架之外的隐含维度；公开来源已可核验框架结构和原始 prompt，但具体内容复制/再发布范围仍需按授权状态控制。

FrameworkResult 绑定 DefinitionVersion、全部相关作答来源和实际评估模式；A7 展示时明确“这是该框架的视角”。需要进入原生 Current Understanding 的候选内容交回 A5 重新检查证据与范围，不允许 FrameworkResult 直接覆盖 Claim。框架中的发展计划交给 A6 作为 ActionProposal；用户接受、修改或拒绝后才决定是否创建 ActionTrial。

### 3.12 洞察分析 Profile

A4/A5 在需要深层解释时可以运行 Insight Analysis Profile：先保留用户呈现的问题，再尝试 reframe；检查当前 life structure 的支撑与缺口；识别有两端证据的 tension；列出主要 hypothesis 与替代解释；最后选择最能区分解释的问题，或在用户愿意时提出一个低负担 experiment candidate。

该 profile 的目标是提高分析质量和可复核性，不是要求系统展示模型内部思维过程。产物只包含可向用户解释的结论结构、证据引用、范围、反例、替代解释与 change condition；不得保存或展示隐藏 chain-of-thought。

有据分析与语义复核使用同一问题/提出者、实际 EvidenceSet、必要情境和旧报告；复核不能遗漏 task 后将问题重构误判为捏造。程序检查引用、资格、依赖和版本；独立语义调用检查立场升级、跨项目类推、真实冲突、修订依据以及追问是否能区分解释。复核失败的草稿保留为 needs_review，不因 JSON 合法而发布，也不把模型复核视为真人正确性证明。分析/复核通过并不绕过来源更正后的发布前再检查。具体切片见 [真实取证与受约束复评](implementation/diagnostic-evidence-reasoning.md)。

Profile 输出不是新的持久真值层。通过 A5 校验的 reframe/tension/hypothesis 进入现有 Claim/ClaimRevision；尚不能区分的解释进入 KnowledgeGap；LifeStructureView/TensionView 仅投影当前 Claim/Gap；现实验证候选进入 A6。若没有足够证据支撑两端，就只能描述候选矛盾或未知，不能为了“洞察感”制造 tension。

### 3.13 诊断编排与三类起步路径

在用户需要综合评估时，由既有 A1/A4/A5/A7 编排诊断，作为使用个人理解的一条路径，不要求日常对话先转成诊断任务。选定的方法及输入要求来自 A9；需要固定工具结果调用 A8，需要完整框架评估调用 A10，两者不混成通用量表。研究支持方法组合选择，框架保持独立版本和结论范围。

零历史由 A1 采集本次问题和少量具体经历；少量历史先复用已有表达再补关键缺口；丰富历史由 A4 依框架问题检索 A3 的片段、情境和反例。三条路径都能生成有限初评，不要求等待离线蒸馏或全部维度完成。历史预填与本轮访谈、模型推断分开，标准量表仍按工具输入条件执行。

DiagnosticRun 保存方法/协议版本、输入模式、EvidenceSet、提问进度和生成状态；A5 形成有范围的判断，A7 输出可版本化报告。报告引用原生 ClaimRevision、框架 FrameworkResult 或量表 AssessmentResult 的确切版本，不把这些结果当作独立个人事实。旧 L3 仅作检索线索；不能只扩写摘要形成完整诊断。

原始输入/更正先可靠保存，再定向更新受影响判断与报告；语义生成失败不阻止更正生效。开始、恢复、补问、反馈、复评、导出为显式操作，GET 不触发付费推理；报告读路径始终检查当前证据/内容可用性。

### 3.14 全量个人理解基线与统一呈现

在 A2/A3 固定的来源/用途范围内，A4 先组织全批主题覆盖与候选情境，A5 对主题作有界分析、检查反例和遗漏，再建立综合基线；A7 在同一 App 呈现总览、专题、框架与变化。该过程不要求用户先输入精确问题，也不能等同于将每个主题都交给所有框架全量重读。
既有单次问题取证、复评和来源校验作为可复用能力，不作为整批内容覆盖的替代。A4 保留未采用、未处理与未知去向；A5 对旧 L3 按当前规则核对，专题和跨专题结论仍追到原始证据，不用摘要彼此自证。
从总览或专题进入 A1 时携带目标报告/认识版本与未决问题；新输入先保存，A5 定向修订，A7 同步变化说明。报告 GET 只读，不触发全量生成；后台原文管理位于二级入口，不再要求用户跳转多个加工查看器。
正式读写继续经同一 Core，本人阶段同样经账号模式，运行真源见 [ADR D23](adr.md#d23-账号模式云端数据库为唯一运行真源其余运行路径冻结或退役)。已有受控私有 adapter 冻结，不作为验收入口；任何路径都不能把文件放进公共静态资源，也不能冒充已完成云端身份、多端同步或完整 HUMAN 3.0。已有全量 AV 交付的覆盖与内容义务见 [统一 App 契约](implementation/av-understanding-app-delivery.md)；新增持续对话和使用闭环按[第一阶段范围](delivery/phase-1-personal-understanding.md)验收，不能用局部可用结果抹去既有未完项。

### 3.15 多端一致性与可选源档

设备通过同一服务端账号与租户上下文读取/修改状态。提交携带幂等键和基准版本；冲突显式处理，不让最后到达的离线消息覆盖新纠正。同步已确认的输入、反馈和诊断版本；本地保留草稿/缓存/待同步操作，在线初版不要求 CRDT 或完全离线诊断。

原始档案托管或仅本地分别记录；主服务保留用户允许的必要摘录、上下文与定位。仅本地源档暂不可用时，仍可读取已有诊断和接收新输入，但需回查未同步内容的请求明确降级。缓存、索引和旧报告不能绕过来源排除或删除。

### 3.16 知识加工与专项路径的协作

本节响应 [BA §9](ba.md#9-知识加工与专项路径的后续业务要求)，只定义模块协作；开发切片与行为用例统一在[专项契约](implementation/knowledge-and-specialized-paths.md)。

**共用主链（KP-R01）。** A2/A3 保存来源版本、作者/对象/立场、覆盖去向、命题与情境；A4 根据本次问题取合格支持和反例，并保留未采用范围；A5 形成有范围的专题及跨事件认识、决定受纠正影响的依赖；A7 只呈现当前版本、缺口和变化。已有 U1/U2 私有加工结果可作为迁入来源，但不能成为普通用户必须运行的另一套后台。

**知识链（KP-R02）。** A9 发布有来源和适用条件的内容版本；A4 可用它选择问题或解释角度，A6 可用它提出候选做法。A5 判断个人材料是否支持关于此人的结论，不能由 A9 的普遍方法主张代替。A7 分开显示个人依据与内容依据，内容停用触发新建议阻断及受影响说明。

学习时的阅读、认同、质疑与实际尝试，分别按其真实语义进入 A2/A3。接触一项理论只证明接触过该内容；用户表达的认识变化可作为新来源，A5 再检查它是否需要修订当前个人理解。知识学习与个人学习反馈在同一产品过程中相接，各自保留来源。

**三种不同专项。** HUMAN 3.0（KP-R03）由 A9 的正式 DefinitionVersion 驱动 A10，仍复用 A1 的逐题输入和 A7 的框架结果呈现。《新世界》（A New Earth，KP-R04）只由 A9 提供作品视角内容，由 A4/A7 在用户选择的事件上展示对照，不进入 A8 计分或 A10 等级。ADHD 支持（KP-R05）由 A1 低负担澄清具体困难，A3 保存情境，A9 提供适用做法，A6 承接用户选择的尝试和回顾；A5 不把功能困难或文学/框架标签自动升级为临床或人格判断。

### 3.17 持续对话使用并更新个人理解

A1 续接当前话题时，A4 读取与本次意图有关的当前 ClaimRevision、经历、约束、未决分歧和最新纠正；有需要时加入 A9 的学术或方法内容。回应可以是理解与开导、解释、建议、质疑或一个有区分力的问题，不能为了积累数据机械追问，也不能因本次无需新增认识就认为对话无价值。

用户新表达先保存为来源。值得保留的变化再由 A3/A5 组织为有范围的认识或修订；系统回应保留其生成版本和引用，不自动成为关于用户的新证据。回应中提出的候选解释与已发布认识分开，用户认可也不独立证明解释成立。

A7 让用户能从一次回应回到当前认识及依据，或从总览/专题进入相关对话。后续回应、总览、专题与建议共享同一当前认识和修订结果；同一入口能保存、恢复及继续使用，具体阶段完成条件见[第一阶段范围](delivery/phase-1-personal-understanding.md)。

## 5. 信息选择和质量特性

检索先确定租户、权限和分析范围，再做相关性选择。优先选择与问题有关、跨独立事件的材料，并为反例、不同时间/情境和最新纠正留出位置。旧模型结论只能帮助定位证据或待核实问题，不能通过重复引用提升自己。

A4 的决策顺序是：用户当下意愿 → 还有没有必要澄清 → 哪条信息能区分解释 → 获得它的负担 → 继续、换题或结束。它不是为了增加轮次而设计的推荐引擎。

引导提问与认识发布在当前设计中按 **Deterministic Gate → Semantic Planner → Deterministic Validator** 执行。资格、版本、open-question、预算/hard cap、幂等和明显重复属于程序规则；“哪一个未知最值得问、不同答案可能怎样改变当前理解”属于语义 Planner；Question/Claim 发布前再检查契约、证据引用、scope、版本和重复。Ask/Stop 约束主动补问，不把普通支持、解释或用户主动续聊一概转换成访谈。后置检查通过只说明满足当前策略，不等于事实正确。

探索质量需要独立评测，不用“JSON 能解析”或“模型自己说 confidence 高”代替。固定合成集至少覆盖 Ask/Stop 是否合适、关键 uncertainty 是否命中、信息增益、重复追问、无依据推断、scope 越界、反例改变认识、证据可追溯和保存/Planner/Synthesis 各阶段延迟；真实 dogfood 补充负担与可理解性，不将私人原话直接固化进 repo fixture。

明确区分“存在来源”“原文匹配”“支持这个说法”“足以扩展适用范围”。技术检查可直接验证前两项；语义支持需要审查和反例检验，不能用有效 UUID 代替。检查失败时修正、缩小范围、标为未验证或仅返回整理，不丢弃已经保存的用户输入。

角色资产从公共内容读取相关来源，个性化推演在本租户内完成。来源/引用不能由模型随意补出；事件包改变或用户纠正后，旧对照标明过期或重新生成。某角色失败只影响其结果，其他结果及原生探索仍可用；引用可定位不等于推演合理。

## 6. 持久化与失败边界

保存输入成功不依赖 LLM 成功；分析失败保留输入并提供明确状态，不重复创建同一来源。耗时处理使用可重试任务；发布新的认识版本和失效旧视图应有一致性边界，避免旧解释在纠正后重新成为当前状态。

任务携带租户、目标版本、来源与证据评估版本、输入集合指纹与处理版本。涉及探索/认识生成时还保留可解析的 Epistemic Policy、prompt、model route/model version 与 validator 版本；规则或模型变化必须能与用户材料变化区分。消费时重新检查授权、排除和过期输入；幂等防止重试重复入库，也防止同源重复计证。错误日志不记个人正文、隐藏推理或密钥。

## 7. AA/DA 一致性要求

A1 的引导来源由 QuestionRecord 保存；A3 的事件由多个 EvidenceSpan 支持且可修订；A5 的认识和证据联系为逐论断关系，不只在整份报告末尾附引用；A6 的结果进入同一 SourceRecord/Event/Claim 链；A7 只投影、不制造证据。

A8 的结果既可重算又与原作答同源；A9 的 ContentClaim / FrameworkDefinitionVersion 与个人 Claim 分属不同证据域，引用方向不赋予内容维护者读取个人资料的权限。A10 的 FrameworkResult 与其作答共享血缘，保持 framework-scoped；只有经 A5 正常验证后，候选解释才可进入原生 Current Understanding。A2 不越过核心修改认识，A4 不直接写“事实”，A7 不自行运行另一套人格算法。新增框架、图查询和更多输入类型只有在 [Roadmap](roadmap.md) 的触发条件成立后再展开。


## 客户端与运行职责的实现解释

按 [ADR D25](adr.md#d25-直接退役两个独立客户端统一使用-appsapp-浏览器入口)，`apps/app` 是唯一浏览器客户端，手机 H5 与桌面同代码；独立 `apps/web`、`apps/miniapp` 已从仓库退役，不等待全部旧功能迁入。App 内部 native/private/diagnostic-preview/dogfood 兼容分支保留，不新增独立真源。客户端退役不扩展为后端、数据库、迁移或用户数据清理，也不证明线上入口已切换。原生 Core 在同一账号数据库与 Profile scope 内运行；U2/dogfood 与私有 U3 只保留既有产物/兼容，不承接新入口；archive 是只读过渡，迁入核对后按 D23 退役。

`wrangler.app.jsonc` 是 assets-only 前端，不需要 main；API 由 `wrangler.jsonc` 的 Worker 提供，App 的 VITE_CORE_API_BASE 必须指向相容 API 并验证 cookie/origin。入口部署、运行数据权威性与代码保留是三个维度，实际部署观察只在 Current Status，不从目录存在推断已上线。
