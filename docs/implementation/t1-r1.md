# T1-R1 — 连续使用与纠错可靠性实施设计

> 本文定义探索的可靠性契约。Start/Respond/Planner/Synthesis 的具体流程统一由 [单次探索契约](t1-purposeful-exploration.md) 定义；本文不保存执行历史或阶段完成状态。

## 1. Outcome Anchor

把已经可运行的单次 FindMe 闭环升级为可持续自用的可靠闭环：

`开始 → 回答 → 关闭/刷新 → 恢复 → 查看依据 → 纠正 → 修订 → 再打开仍是最新版本`

同时保证：

- 弱网/响应丢失重试不重复写入；
- 多步领域写入要么全部提交，要么全部回滚；
- 并发或生成期间发生新修改时，旧结果不得覆盖新状态；
- 来源被排除后，依赖它的当前认识立即停止作为“有效当前认识”展示；
- 证据不足、全部撤回和没有结论都是合法成功结果。

本批不做：历史全量导入、跨 Experience 综合、完整三观报告、多角色、行动试验、正式多用户认证、图数据库、legacy 全面退役。

## 2. 固定实施原则

1. LLM 调用在数据库 transaction 外；最终发布在短 transaction 内。
2. 所有会改变探索事实的操作绑定 `exploration.version`；过期生成绝不发布，也不自动 merge。
3. 所有 mutation 使用 `Idempotency-Key`；相同 key + 相同请求只产生一次领域写入。
4. 来源撤销/排除是确定性数据操作，先立即停止旧认识生效；重新解释是后续动作，不和撤销绑定。
5. 原始 Source/Evidence/历史 Revision 不静默改写；修订通过新版本和状态表达。
6. Core API 返回稳定错误码/状态，客户端不得解析中文 message 决策。

## 3. 状态模型

### 3.1 Exploration

持久状态：

- `active`
- `completed`
- `abandoned`

新增字段：

- `version INTEGER NOT NULL DEFAULT 1`
- `last_activity_at timestamptz NOT NULL DEFAULT now()`

API 派生 phase：

- `ready_to_plan`：输入已保存，当前没有 open question 或最终认识，等待 Planner
- `awaiting_answer`：存在 open question
- `review`：存在有效 current claim，可查看/纠正/继续
- `insufficient`：无有效 claim，但存在 gap
- `needs_review`：存在 current claim，但证据状态 stale/invalid
- `completed`：exploration 已完成

### 3.2 ExplorationQuestion

新增：

- `status = open | answered | skipped | superseded`
- `answered_at`

约束：同一个 exploration 同时最多一个 `open` question。

`next_question` 不再作为可恢复流程的唯一载体；继续探索必须创建真实 Question 记录及 ID。

### 3.3 ClaimRevision

现有生命周期状态 `current/superseded/withdrawn` 继续回答“哪个版本是当前版本”。

新增独立证据状态：

- `valid`
- `stale`
- `invalid`

新增：

- `invalidated_at`
- `invalidation_reason`

Current Understanding 默认只把 `status=current AND evidence_status=valid` 放入有效 claims；stale/invalid 进入 `needs_review`。

## 4. 幂等与 Operation

新增 `core_operations`：

- id
- tenant_id / subject_id
- exploration_id nullable
- idempotency_key
- operation_type
- request_hash
- status = processing | completed | failed | stale
- basis_version nullable
- lease_expires_at
- response_status nullable
- response_body nullable
- created_at / completed_at

唯一约束：`(tenant_id, idempotency_key)`。

规则：

- 相同 key + 相同 request_hash + completed：直接返回第一次结果；
- 相同 key + 不同 request_hash：409 `IDEMPOTENCY_KEY_REUSED`；
- 相同 key + processing 且 lease 有效：202 `OPERATION_IN_PROGRESS`；
- failed 且没有领域提交：允许相同 key 安全重试；
- 最终领域写入和 operation=completed 必须在同一个短 transaction 中提交。

首批 mutation：

- POST /explorations
- POST /explorations/:id/respond
- POST /explorations/:id/correct
- continue / complete / source assessment / amend

都要求 `Idempotency-Key`。

## 5. 乐观并发

会改变既有 exploration 的请求必须带：

`expected_version`

流程：

1. preflight 读取 exploration/version 和输入快照；
2. 如需生成派生结果，在 transaction 外调用模型；
3. commit transaction 开始时执行条件更新：
   `UPDATE explorations SET version=version+1 ... WHERE id=? AND version=expected_version`
4. affected rows = 0：整个 transaction rollback，返回 409 `STALE_VERSION`。

Correct 额外要求所有 `claim_revision_ids` 在最终 commit 时仍为 `status=current`；否则 409 `STALE_CLAIM_REVISION`。

不自动 merge 两个并发 correction。客户端 reload 最新版本，同时保留用户未提交/失败的 correction draft。

## 6. 原子写入

Respond 的 commit transaction 至少包含：

- exploration version bump
- answer SourceItem
- SourceAssessment
- EvidenceSpan
- ExperienceEvidence
- ExplorationTurn
- Question -> answered
- CoreOperation -> completed

Correct 的 commit transaction 至少包含：

- exploration version bump
- current ClaimRevision precondition
- correction Source/Evidence/Turn
- FeedbackEvent
- 新 ClaimRevision / withdrawal
- ClaimEvidence
- KnowledgeGap replace
- CoreOperation -> completed

Respond 只保存回答，不生成认识。Continue 的发布边界见单次探索契约；Correct 的模型/结构/业务校验失败不提交修订，也不覆盖既有认识。

## 7. 恢复与继续

### GET /api/core/explorations

首批支持：

- `status=active|completed`
- `limit` 默认 20

返回摘要、version、phase、last_activity_at 和 open_question 摘要。

### GET /api/core/explorations/:id

升级为恢复真源，返回：

- id/version/status/phase
- experience
- open_question
- turns
- understanding { outcome, claims, gaps, needs_review }
- evidence

App 刷新/重启后只依赖此接口恢复，不依赖 React 内存。

### POST /api/core/explorations/:id/continue

承接已保存输入，执行 Planner 及必要的最终综合，具体契约见单次探索文档。本接口同样执行幂等、version precondition 和短事务发布。

### POST /api/core/explorations/:id/complete

输入：expected_version。幂等、version protected。完成后不再进入 active 列表。

## 8. 来源评估与传播

### POST /api/core/sources/:id/assessment

输入：

- expected_assessment_version
- attribution_status
- context_completeness
- temporal_precision
- eligibility
- rationale

原 SourceItem 不改；旧 SourceAssessment `is_current=false`，创建下一版本。

确定性传播：

1. 找到该 source 的 EvidenceSpan；
2. 找到依赖这些 span 的 `status=current` ClaimRevision；
3. 如果该 revision 仍有其他 eligible 支撑证据：`evidence_status=stale`；
4. 如果没有任何 eligible 支撑证据：`evidence_status=invalid`；
5. Current Understanding 立即停止把 stale/invalid 当有效 claim；
6. 不自动生成替代解释。

当前实现将来源相关探索的锁定和认识失效集中在 `core/source-invalidation.ts`，原生评估和账号来源生命周期共同调用；必须先取得探索锁，再修改来源/评估，等待后重新核对版本。判断剩余支持时同时检查来源使用状态与当前评估资格，不能让已重绑排除的来源仅凭旧 eligible 标签继续有效。硬删除清理正文属于不同操作，不用本节软失效行为代替。

`not_mine` UI 落到具体 Evidence/SourceAssessment，而不是只给 Claim 记“不准确”。

## 9. 空结果契约

首次综合要求 claims/gaps 至少一项存在；全部撤回的修订允许两者均为空。集合上限与字段定义以 Core schema 为准。

outcome：

- `provisional`：存在有效 claim
- `insufficient`：claims=[] 且存在 gaps
- `withdrawn`：本次修订后所有目标 claim 均撤回且没有替代 claim

全部撤回是成功结果，不要求模型硬造新解释；HTTP 状态以接口契约和测试为准。

Current Understanding：

- `state=current`
- `state=empty`
- `state=needs_review`

## 10. 错误契约

Core 稳定 code：

- EXPLORATION_NOT_FOUND — 404
- QUESTION_NOT_OPEN — 409
- STALE_VERSION — 409
- STALE_CLAIM_REVISION — 409
- IDEMPOTENCY_KEY_REUSED — 409
- OPERATION_IN_PROGRESS — 202
- SOURCE_VERSION_CONFLICT — 409
- LLM_UNAVAILABLE — 503

`NO_ELIGIBLE_EVIDENCE` 优先表达为 `outcome=insufficient`，而不是技术错误。

## 11. 前端状态

首页提供探索恢复入口，状态展示与持久状态一致。

恢复 phase：

- ready_to_plan → 输入已保存，可进入 Planner
- awaiting_answer → 问题页
- review → 当前理解页
- insufficient → “目前还不足以形成认识”，允许继续/结束
- needs_review → “有依据发生变化”，允许查看影响/重新评估
- completed → 历史只读，可查看 evidence；纠正历史时仍走 version/current revision 检查

弱网/冲突：

- 202 operation processing → 轮询 operation；
- STALE_VERSION → 自动 reload 最新版本，保留 correction draft；
- 重试复用同一个 Idempotency-Key。

## 12. 冻结验收案例

1. Respond 同 key 重放：仅 1 份回答 Source/Turn，不触发认识生成。
2. 服务器成功但 response 丢失：重试返回第一次结果，不重复写。
3. 相同 key 不同 payload：409。
4. 两个 Correct 同时针对 version N：一个成功，一个 STALE_VERSION。
5. 模型生成期间发生 correction/source exclusion：旧生成不能发布。
6. 排除唯一支持来源：Claim 立即退出有效 Current Understanding。
7. 排除部分来源：相关 Claim 进入 needs_review。
8. attribution subject -> other：本人观点关系停止生效。
9. 所有 Claim 撤回：成功返回 outcome=withdrawn。
10. 首轮证据不足：成功返回 outcome=insufficient。
11. App 在 question/result 页面关闭后可恢复同一 exploration。
12. complete 后不再出现在 active 列表。
13. bootstrap 单次/过期规则保持现状。
